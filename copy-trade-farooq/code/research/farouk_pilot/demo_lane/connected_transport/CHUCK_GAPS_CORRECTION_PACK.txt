1. AMBIGUOUS SEND CLASSIFICATION (correction 1) — transport.py
--------------------------------------------------------------------------------
The forget-and-SEND_FAILED-on-any-exception behaviour is REMOVED for every connector.
A. DEFINITELY_NOT_SENT — allowed ONLY provably before the first transmit attempt:
     state/gate refusal (raises before a correlation exists), encoding/framing failure,
     connector not connected before send starts (checked caller-side AND sender-side).
     ONLY this path releases (forgets) the correlation; a deliberate re-issue then succeeds.
B. OUTCOME_UNKNOWN — ANY error raised once connector.send begins (sendall proves nothing):
     correlation RETAINED + marked OUTCOME_UNKNOWN; NO automatic retry; READY invalidated;
     transport disconnects; after reconnect the full sequence re-runs and the transport is
     RECONCILE_ONLY until reconciliation completes; only then may anything be deliberately
     re-issued (new-session correlation; the ambiguous one stays OUTCOME_UNKNOWN forever).
Tests (suite section 7): encode-failure -> DEFINITELY_NOT_SENT + release + re-issue OK;
not-connected-before-send -> DEFINITELY_NOT_SENT + release; raise with zero/unknown bytes ->
OUTCOME_UNKNOWN; PREFIX-transmitted-then-raise -> OUTCOME_UNKNOWN; COMPLETE-frame-then-raise
(broker provably received; response lost) -> OUTCOME_UNKNOWN; no correlation forgotten on any
ambiguous path (checked after reconnect too); action refused from DISCONNECTED; reconnect ->
auth -> reconcile PRECEDES any new open (broker-seen ordering asserted).

2. ONE ALWAYS-ON I/O OWNER (correction 2) — transport.py
--------------------------------------------------------------------------------
One transport-owned reader thread is the ONLY caller of connector.recv: continuously reads
while connected, deframes everything (combined + fragmented preserved — same Deframer), routes
matched responses by clientMsgId to waiting callers (futures), consumes async fills/events even
when no request is awaiting (fail-closed for unknown ones). One sender thread drains the ONE
outbound queue (fresh per session — stale frames can never be resent) and emits heartbeats
AUTOMATICALLY when idle >= HEARTBEAT_INTERVAL_S (10s). Request callers submit to the queue and
wait on a response future; they never call recv. Disconnect deterministically stops both loops
(generation counter), wakes every pending caller as OUTCOME_UNKNOWN (correlations retained),
and invalidates READY; reconnect re-runs the full auth + reconcile sequence before any action.
Tests (suite sections 10, 11, 16): ack now + fill later with NO second request -> consumed;
async STOP_MOVED while idle -> consumed; heartbeat emitted automatically (no manual call;
interval <= 10s asserted); two requests answered in REVERSE order -> each routed to its own
caller by clientMsgId; response + async event in the SAME frame batch -> both processed;
exactly ONE reader thread and ONE sender thread touch the socket (thread-identity instrumented;
never the caller); disconnect wakes a blocked caller promptly as OUTCOME_UNKNOWN (measured well
under the response timeout; nothing left PENDING); reconnect -> READY and actions resume only
after reconciliation.
