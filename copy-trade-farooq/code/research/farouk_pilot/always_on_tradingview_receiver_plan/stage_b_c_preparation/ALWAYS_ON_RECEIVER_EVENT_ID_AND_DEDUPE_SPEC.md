# Always-On Receiver — event_id & Dedupe Spec

**Mode: PREPARATION / DESIGN ONLY.** Defines identity + deduplication for the always-on receiver.
Consistent with Stage 1/2 behaviour and the append-only-on-R2 model.

## event_id

- **Purpose:** unique identity per received request; primary key; R2 object key anchor; idempotency
  handle.
- **Value:** a UUIDv4 or ULID generated by the receiver at receipt. (In a Worker, `crypto.randomUUID()`.)
- **Uniqueness:** every accepted request gets a fresh `event_id` — including duplicates (a duplicate is
  a distinct *record* flagged as such; it is not merged into the original).
- **R2 key:** `events/YYYY/MM/DD/<event_id>.jsonl` — because the key is unique, R2 `put` never
  overwrites an existing object → **append-only guarantee** holds even on a key-value-style store.

## dedupe_key (semantic dedupe, separate from event_id)

- **Purpose:** detect TradingView **retries** / repeats of the *same firing*, while keeping genuinely
  distinct firings separate. Mirrors the 111→90 CSV dedup and the Stage-2 receiver.
- **Formula:**
  `dedupe_key = sha256( alert_name | symbol | timeframe | trigger_time | event_text_normalised )`
  - `event_text_normalised` = trimmed, lowercased, collapsed-whitespace form of the event/description
    text (or the raw body if not JSON).
  - If `trigger_time` is missing → fall back to a **coarse `received_at_utc` bucket** (e.g. minute) and
    set `notes = "dedupe_degraded_no_trigger_time"`. Never silently.
- **Not** based on `event_id` (which is always unique) or `received_at_utc` alone (retries arrive at
  different receipt times).

## Duplicate handling

- Compute `dedupe_key`. If it matches a prior **ACCEPTED** record's key:
  - Store the new record **append-only** (own `event_id`, own R2 object) with
    `validation_status = DUPLICATE`.
  - It is **excluded from distinct-event counts** at report time, **not dropped** at ingest.
- Duplicate detection needs to see prior keys. Options for the Worker:
  1. **Index object** — maintain an append-only `dedupe/<key>` marker object; a `head`/`get` on that
     key tells you if the firing was seen. (Cheap, eventually-consistent; acceptable — a rare missed
     dedupe just yields a second ACCEPTED that a later report can collapse, never data loss.)
  2. **Report-time dedupe** — accept everything append-only, compute distinct events in the read-only
     parser/report stage (Stage I). Simplest and fully lossless; recommended first.
- **Recommendation:** rely on **report-time dedupe** (option 2) for correctness, optionally add the
  index-object (option 1) for live duplicate flagging. Either way, **nothing is ever dropped at
  ingest** — raw-first, append-only is preserved.

## Why this is safe

- Identity (`event_id`) and semantic dedupe (`dedupe_key`) are separate, so append-only integrity is
  never in tension with duplicate detection.
- No record is ever overwritten or deleted; dedupe only affects *counting*, never *storage*.
